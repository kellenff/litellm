# Concept: Model-scoped token-plan credential with ordinary fallback

- **Slug**: codex-token-plan-auto-router
- **Created**: 2026-10-27
- **Revised**: 2026-10-28, after the operator proposed a model-level configuration for the token-plan header and ordinary fallback on a 400
- **Recommended option**: B (Model-scoped token-plan forwarding), delivered on top of A (configure, do not add code)
- **Not recommended**: C (Classify plan failures and react), because it depends on recognizing upstream prose that the research shows is not a contract, and because the operator's proposed design makes that classification unnecessary. Reopen it if upstream starts returning a stable machine-readable eligibility signal, or if operators need a plan-ineligible 400 to stop the fallback chain rather than hand the request to the fallback model

## Options

### Option A - Compose the behavior out of what already exists

- **Sketch**: The operator keeps one model group per credential-bearing deployment, exactly as today: a ChatGPT Codex group whose deployment carries the plan credential (a stored `chatgpt_auth_file`, or the caller's own forwarded bearer that PR #41522 already ships), and an ordinary group whose deployment carries its usual `api_key`. The auto-router's routes point at those group names, so a request that lands on a Codex group is authenticated by the plan credential and a request that lands on the ordinary group is authenticated normally, with no new concept in the proxy. Plan ineligibility surfaces to the caller as whatever upstream returned, and the router's existing fallback path carries the request to the next configured group
- **Appetite**: small (configuration and documentation, days at most)
- **Trade-offs**: Wins immediately with zero new credential surface, so the existing provider isolation, the server-owned credential rules, and the shipped client-subscription forwarding all keep working untouched. The credential does follow the selected target, because in LiteLLM the target is a deployment and the deployment owns the credential. Sacrifices everything the problem asks for beyond that: no notion of which models the plan covers, so the operator hardcodes a mapping that goes stale whenever the plan changes (research shows the plan changes without notice), no distinction in logs between a plan-ineligible target and an ordinary bad request, plan-covered traffic still reads as zero cost because every `chatgpt/` row in the cost map carries no rates, and the semantic auto-router cannot attach a per-route credential at all, so any route that needs a specific ChatGPT account needs its own group or the complexity router instead
- **Rabbit holes**: The group-per-credential layout grows with the number of accounts and the number of plans, and the operator has to keep the route-to-group mapping in sync with a policy the proxy cannot see. A stale mapping does not fail loudly, it silently routes a plan-covered model to a metered credential or the reverse. Operators reading the shipped guide are told explicitly not to configure cross-provider fallbacks for subscription traffic, so the "lands on the wrong group" case is one the docs advise against having

### Option B - Model-scoped token-plan forwarding with ordinary fallback

- **Sketch**: The operator declares, per model or model group, that the client's forwarded ChatGPT bearer is the credential for that target, and the router forwards the bearer only when the selected deployment matches a declared scope. Everything else is unchanged: a target that is not in scope uses its own configured credential, and the caller never sees a credential swap. The scope is enforced at the point where the router already binds a credential to a selected deployment, so it composes with the existing per-request deployment mechanism rather than adding a new credential surface. This narrows what the proxy does today, where the scope is the provider rather than the model, so a forwarded bearer currently reaches every ChatGPT deployment and therefore also reaches a ChatGPT model that happens to be the fallback target, and reaches one even when the client originally asked for a different provider. When the plan-backed target rejects the request with a 400, the router's existing fallback path takes the request to the configured fallback model, which is out of scope and therefore authenticates normally. The proxy does not try to tell a plan rejection apart from an ordinary bad request, and it does not try to predict eligibility before the request is attempted
- **Appetite**: small to medium (days to weeks), and it depends on whether the declared scope is expressed as a model list on the deployment, on the model group, or as an existing header-scoping mechanism reused for a new purpose
- **Trade-offs**: Wins the part of the problem that configuration alone cannot reach, because the operator can expose one client-facing name over both plan-backed and ordinary models and have the credential follow the router's choice without maintaining a second mapping. It reacts to ground truth, so it needs no local copy of OpenAI's entitlement policy, and it therefore cannot go stale the way an operator-maintained coverage list does: a stale entry only causes one failed round trip and a fallback, which is the ordinary behavior of any other upstream rejection. It keeps the deployment as the only place a credential lives, so the existing isolation rules stay as they are and no new server-owned credential field is introduced. It sacrifices the distinction between a plan rejection and an ordinary bad request in the proxy's own behavior and its logs, because the operator has chosen the ordinary path, so the operator learns the request was plan-ineligible by reading the upstream message rather than from the proxy's own classification. It also does not by itself make plan-covered traffic visible in the spend view, since every `chatgpt/` row in the cost map still carries no rates, and it does not cover the exhaustion case, which is a 429 that the router already retries and cools down generically
- **Rabbit holes**: The scope has to be enforced at the same moment the router resolves the credential for the selected deployment, because that is the only point where the selected target is known, and the request that carries a forwarded bearer and the request that carries the deployment's own credential must not be able to end up with both. The fallback hop re-resolves a deployment, so the scope has to be re-evaluated per hop rather than decided once for the request, or a fallback target could inherit the plan credential it was never scoped for. The forwarded bearer reaches the upstream by two independent routes, the router's substitution of it as the deployment's key and the merge of the scoped header into the outbound headers, and both are keyed on the provider today, so a scope that gates only one of them still lets the bearer reach an out-of-scope ChatGPT model through the other. And the model-group-scoped header forwarding that already exists in the proxy forwards only the `x-` headers and the Anthropic beta header, not the authorization bearer, so it is a pattern to follow rather than a mechanism to reuse. And the ordinary fallback on a 400 depends on the router's `fallback_on_unsupported_params` setting, which defaults to on, so a 400 falls back as the operator expects, but the proxy's own router settings default it to unset, which the router reads as on, so an operator who has explicitly turned it off in their configuration would see a 400 stop the fallback chain instead of reaching the fallback model

### Option C - Classify plan failures and react to them

- **Sketch**: Keep the credential where it belongs, on the deployment, and instead make the proxy understand the two ChatGPT-specific failure shapes it currently cannot tell apart: a target the account's plan does not cover, and an exhausted usage allowance. When the router sees the plan-ineligible shape it treats it as a routing outcome rather than a terminal error, so it stops trying that target, moves on to the next configured group with that group's own credential, and records that the request was served under a different credential class than the one the caller supplied. When it sees the exhaustion shape it cools down that target without silently substituting a metered target, because that substitution is exactly the surprise the shipped guide warns about. Every request records which credential class served it, so a plan-covered call is visible as such in the logs and in the spend view even though its row has no per-token rates
- **Appetite**: medium (weeks), and the estimate depends on whether upstream's plan-ineligible signal can be recognized without depending on its exact wording, which is an open question rather than a settled fact
- **Trade-offs**: Wins the parts of the problem that no amount of configuration can supply, which is telling the operator and the caller that a target was outside the plan, keeping a plan failure from looking like an ordinary upstream bug, and making the credential substitution visible after it happens. It reacts to ground truth, so it does not need a local copy of OpenAI's entitlement policy, and it therefore cannot go stale the way an operator-maintained list does. It also leaves the deployment as the only place a credential lives, so no new server-owned credential field is introduced and the existing isolation rules stay as they are. It sacrifices the ability to avoid the ineligible request in the first place: the first attempt to a plan-ineligible target still costs a failed round trip and still needs the target to be listed as a route, so the operator still maintains a list of candidate groups, just one that is allowed to be wrong without being silently wrong. And it does not deliver the single-alias experience where one name carries both a proxy-held plan credential and a metered credential, because that remains a per-group property
- **Rabbit holes**: The upstream plan-ineligible signal is a 400 with a prose message, and prose is not a contract, so the classifier needs a rule that survives rewording, and a wrong classification either masks a real upstream bug or retries a target that will never work. The exhaustion case is a 429 that the router already retries and cools down generically, so the change has to distinguish "this target is temporarily unusable" from "this target is permanently unusable for this account" without disturbing the existing retry and cooldown behavior for every other provider. When the credential came from the caller rather than the deployment, the record of which credential served the request has to be captured at call time, which is where the existing request metadata and the per-request deployment identity already live. And the cost surprise is a policy decision the operator has to opt into explicitly: substituting a metered target after a plan failure is a legitimate request and also a billable one

## Recommendation

Recommend B, built on top of A

A alone already delivers the visible outcome the idea asks for: one client-facing name, a credential that follows the selected target, and normal proxy auth when a different model is picked. B is the increment that makes the credential follow the *routing decision* rather than the *static target*, which is what the intake asked for and what the operator proposed. It also delivers the fallback behavior the operator asked for, a 400 on the plan-backed target handing the request to the configured fallback model, using the router path that already exists

B is the option that does not require the proxy to know more than it can know. C's premise is that the proxy can tell a plan rejection from an ordinary upstream rejection, and the research contradicts that premise: upstream enforces entitlement server-side, produces the same error for an expired subscription, a plan downgrade, and a retired model, and has no stable machine-readable signal today. B sidesteps that entirely by treating the 400 as an ordinary rejection and letting the fallback chain do what it already does, which is why the operator's proposal and the research agree even though they were reached independently

B is also small enough to try before committing to it, because the forwarding mechanism it reuses is already in place. The router already computes a forwarded authorization from the request's scoped headers and binds it to the selected deployment through a per-request deployment that is deliberately never registered with the router, and the ChatGPT provider already prefers a forwarded client credential over a configured key. What B changes is which deployments that mechanism applies to, not the mechanism itself. That keeps the blast radius away from the part of the design where an open credential-leak bug already lives

A should ship first and independently. It costs configuration and a guide, it gives operators a working arrangement before any code lands, and it gives B a real configuration to be tested against

Do not build C on the evidence available. If it is wanted later, it should be reconsidered when upstream exposes a stable per-account eligibility signal, and it should be treated as a new assessment with its own error-classification analysis rather than an extension of this one

## Out of Scope (for the recommended option)

- A local copy of OpenAI's plan-to-model entitlement policy, and any attempt to predict eligibility before a request is attempted
- Distinguishing a plan rejection from an ordinary upstream 400 in the proxy's own behavior or its logs, which the operator has explicitly traded away in favor of the ordinary fallback path
- Changing the behavior of a 429, which stays on the router's existing retry and cooldown path
- The Codex-native passthrough route as a routing surface, since it forwards verbatim and never consults the router
- Any change to the credential precedence that shipped for the existing single-model ChatGPT subscription flow
- Making the upstream credential a client-selectable request parameter, or widening which providers may receive a forwarded credential
- The Anthropic subscription provider, which has its own open request
- Subscription account management in the dashboard
- Per-token pricing for subscription models, beyond making plan-covered traffic identifiable in the logs and the spend view
- Deciding the exhaustion substitution policy on the operator's behalf, which stays an explicit opt-in

## Assumptions to Validate

- [NEEDS CLARIFICATION: the token plan credential is the caller's own forwarded bearer, as PR #41522 ships today, rather than a credential the proxy holds. The operator's proposal speaks of proxy-passing a header, which points at the forwarded bearer, and the options differ sharply here, since A and B assume the former and only C's proxy-held variant assumes the latter]
- The scope can be expressed in the existing configuration vocabulary without widening the server-owned credential surface, and the operator's intent is a list of models or model groups rather than a per-deployment boolean
- A plan rejection upstream and an ordinary bad request are close enough in effect that treating them alike is acceptable, since the request still reaches the fallback model either way and the operator reads the upstream message when they need the reason
- The fallback model is one the operator is willing to bill, since the ordinary fallback path treats a plan rejection as any other rejection and the shipped guide warns that cross-provider fallbacks incur separate charges
- The exhaustion case does not need to reach the fallback model, since a 429 stays on the existing retry and cooldown path and the operator accepts that an exhausted plan does not silently substitute a metered target
- The operator is willing to give up the goal of a plan-covered request reporting a labeled spend, since the cost map carries no rates for `chatgpt/` rows and that work is separate from the routing change
- The operator does not have `fallback_on_unsupported_params` turned off in their router settings, since the ordinary fallback on a 400 depends on it and the router's own default has it on
- Narrowing the forwarded credential's scope from the provider to the model does not break an existing deployment that relies on the current provider-wide behavior, which is the case for any operator running more than one ChatGPT deployment today
- The caller of a plan-backed route supplies its own ChatGPT bearer, which is the case the shipped forwarding covers, and the proxy-held login remains a separate concern that this scope does not change
