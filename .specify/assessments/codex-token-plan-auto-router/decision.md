## Verdict & Rationale

Go. Problem validity and evidence strength clear the gate, a shaped concept with a layered recommendation exists, and the risk picture is understood rather than ignored

The evidence is strong where it matters most, which is the mechanism. Every load-bearing claim in the concept was re-verified against the current tree during this stage: the provider-scoped forwarded bearer, the per-request deployment that is never registered with the router, the ChatGPT credential precedence that prefers a forwarded client credential, the 400-to-fallback gate, the router's `fallback_on_unsupported_params` default of on, and the absence of any token-plan concept anywhere in the codebase. The concept's recommended option is also the same design the operator proposed mid-pipeline, so it carries operator buy-in that the earlier Option B recommendation did not

The revised recommendation is the layered one, and a go on it commits to the whole stack. Option A, the configuration-only composition that keeps one model group per credential-bearing deployment, ships first and independently, because it costs configuration rather than code and gives operators a working arrangement before any implementation lands. Option B, the model-scoped token-plan forwarding, is the increment that makes the credential follow the routing decision rather than the static target. Both are in scope for the handoff, and Option A's independence is a delivery-ordering fact, not a hedge

The concept's rejection of Option C stands. Its reopening condition was a stable machine-readable upstream eligibility signal, and that condition is still unmet. Upstream continues to return the same prose error, with open issues #14190, #47784, and #42944 all describing "not supported when using Codex with a ChatGPT account" for different underlying reasons, a plan change, an expired subscription, and a rollout, which is the clearest possible demonstration that prose is not a contract. The research file's claim that Option C depends on that signal holds

Two evidence corrections were found while re-checking, and neither changes the verdict. PR #41928, which the research file listed as open, has closed unmerged, so per-model `chatgpt_auth_file` support for multiple ChatGPT accounts is not landing through that route, which widens the gap this idea addresses rather than narrowing it. The research file's other demand citations were re-checked and remain accurate, with #23777 still open and #42172 still an open credential-leak bug in the same class

The one genuinely open question, whether the token plan credential is the caller's forwarded bearer or a proxy-held login, does not block the go. The concept's recommended options both assume the forwarded bearer, which is what the operator's own proposal describes, and Option A works under either reading. The alternative is recorded as a carried-forward question for the specification, not as a blocker

## If go - Handoff to `/speckit-specify`

- **Problem**: An operator who fronts ChatGPT-subscription Codex models and ordinary models behind one LiteLLM proxy cannot expose a single client-facing entry point whose upstream credential follows the model the router actually selected, because the proxy holds no representation of which models a plan covers and it binds credentials to deployments rather than to selections. The outcomes the operator cannot currently tell apart are a request rejected upstream because the selected model is outside the caller's plan, a request that quietly ran on the wrong credential, and a plan-covered request that reports no spend at all
- **Chosen approach**: Option B, model-scoped token-plan forwarding, delivered on top of Option A, configuration-only composition. The operator declares, per model or model group, that the client's forwarded ChatGPT bearer is the credential for that target. The router forwards the bearer only when the selected deployment matches a declared scope, enforced at the point where the router already binds a credential to a selected deployment. A target outside the scope uses its own configured credential. When a plan-backed target rejects a request with a 400, the router's existing fallback path takes the request to the configured fallback model, which is out of scope and therefore authenticates normally. The proxy does not classify plan rejections separately and does not predict eligibility before the request is attempted
- **In scope / out of scope**: In scope is the model-scoped forwarding decision, its enforcement at selected-deployment credential binding, per-hop re-evaluation so a fallback target never inherits an out-of-scope plan credential, and the operator-facing configuration for declaring scope. Option A's configuration-only composition ships first and independently. Out of scope is a local copy of OpenAI's plan-to-model entitlement policy or any attempt to predict eligibility before a request is attempted, distinguishing a plan rejection from an ordinary upstream 400 in the proxy's behavior or logs, any change to 429 handling which stays on the existing retry and cooldown path, the Codex-native passthrough route as a routing surface, any change to the shipped single-model ChatGPT subscription credential precedence, making the upstream credential a client-selectable request parameter, the Anthropic subscription provider, subscription account management UI, per-token pricing for subscription models beyond making plan-covered traffic identifiable, and deciding the exhaustion substitution policy on the operator's behalf
- **Success metrics**: One client-facing name covers both plan-eligible and ordinary targets, with the credential determined by the selected target rather than by static per-target configuration, which is the baseline-to-target move from one model name per credential plus separate fallback configuration. No plan credential is sent to a target outside the declared scope, and no request fails only because of the routing step. The operator can tell from the proxy's logs which credential a given request used. Note that the plan-ineligibility classification metric and the nonzero-spend metric from the problem definition are deliberately not carried, because the operator traded both away in favor of the ordinary fallback path, and the cost map still carries no rates for `chatgpt/` rows
- **Carried-forward open questions**:
  - [NEEDS CLARIFICATION: whether the token plan credential is the caller's own forwarded bearer, as PR #41522 ships today, or a credential the proxy holds via a per-deployment `chatgpt_auth_file`. The recommended options assume the forwarded bearer, which matches the operator's proposal, and Option A works under either reading, but the two differ in isolation guarantees and the specification should settle it before implementation]
  - The exact configuration vocabulary for the scope, whether it is a model list on the deployment, on the model group, or a reuse of an existing header-scoping mechanism, which is open because the closest existing precedent, `ModelGroupSettings.forward_client_headers_to_llm_api`, forwards only the `x-` headers and the Anthropic beta header rather than an authorization bearer, and the `forward_client_headers_by_model_group` identifier in `litellm/types/router.py:181` is a `Literal` member of `OptionalPreCallChecks` with no field and no enforcement behind it
  - How the scope gates both independent routes the bearer travels, the router's substitution of it as the deployment's key and the merge of the scoped header into the outbound headers, since gating only one still lets the bearer reach an out-of-scope ChatGPT model through the other
  - Whether narrowing the forwarded credential's scope from the provider to the model breaks an existing deployment that relies on the current provider-wide behavior, which is the case for any operator running more than one ChatGPT deployment today
  - Whether the operator's configuration has `fallback_on_unsupported_params` turned off, since the ordinary fallback on a 400 depends on it and the router's own default has it on
  - The spend and labeling rule for plan-covered traffic, which remains a separate piece of work because every `chatgpt/` row in the cost map carries no rates
  - The exhaustion policy, whether an exhausted plan may silently substitute a metered target, which stays an explicit operator opt-in and out of scope here
