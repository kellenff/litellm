# Idea Research: Auto-router passthrough for ChatGPT Codex models on a token plan

- **Slug**: codex-token-plan-auto-router
- **Created**: 2026-10-27
- **Evidence confidence (overall)**: medium

## Users & Demand

- LiteLLM issue #23777 "support multiple ChatGPT OAuth accounts in a single LiteLLM instance" is open with 45 `+1` reactions and 7 comments, which is the strongest single demand signal found in this repo for per-account ChatGPT OAuth handling — [source: https://github.com/BerriAI/litellm/issues/23777 | allowlisted host] (confidence: high)
- LiteLLM issue #46062 "[Feature]: Per-user ChatGPT subscription passthrough for Codex-compatible clients" was filed and then closed by the merged PR #41522, so the "forward a caller's own ChatGPT subscription through the proxy" half of the idea already shipped — [source: https://github.com/BerriAI/litellm/issues/46062, https://github.com/BerriAI/litellm/pull/41522 | allowlisted host] (confidence: high)
- PR #41522 "feat(chatgpt): forward client subscriptions through the gateway" merged on 2026-10-26 with 2547 additions across 43 files, and touched `litellm/router.py`, `litellm/proxy/litellm_pre_call_utils.py`, and the ChatGPT transformations — [source: https://github.com/BerriAI/litellm/pull/41522 | allowlisted host] (confidence: high)
- Open follow-on work in the same area shows the feature is still in flux: PR #41928 "support per-model `chatgpt_auth_file` for multiple ChatGPT accounts" is open with 21 changed files, issue #40893 (web UI management for ChatGPT/Codex subscriptions) is open, issue #43925 (enable the new chatgpt subscription login) is open, issue #43572 (isolate cooldown for a forwarded Claude subscription OAuth bearer so fallback works) is open, and issue #42172 (a third-party `api_base` under `anthropic/` receiving the client's Claude subscription credential) is an open credential-leak bug with 8 comments — [source: https://github.com/BerriAI/litellm/issues/40893, https://github.com/BerriAI/litellm/pull/41928, https://github.com/BerriAI/litellm/issues/43572, https://github.com/BerriAI/litellm/issues/42172 | allowlisted host] (confidence: high)
- The demand for the *combination* in this idea (an auto-router that picks among plan-covered ChatGPT Codex models and ordinary models, swapping auth accordingly) is not visible as a filed issue. Searches for "auto_router chatgpt", "codex subscription auto router", "chatgpt codex router model", and "complexity_router codex" over LiteLLM issues returned nothing matching that combination — [source: https://github.com/BerriAI/litellm/issues?q=is%3Aissue+chatgpt+codex | allowlisted host] (confidence: medium)
- Upstream demand signal for plan-scoped Codex access is real and large: openai/codex issue #14190 ("Codex 5.4 / 5.3-codex models fail with 'not supported for ChatGPT account' error") has 7 `+1` and 9 comments, and the thread's resolution is that the reporter's Plus subscription had expired, which is the same class of failure this idea would need to distinguish from an ordinary routing failure — [source: https://github.com/openai/codex/issues/14190 | allowlisted host] (confidence: high)
- Upstream openai/codex issue #53020 shows the plan type is carried on the OAuth token's `id_token` and can go stale: after an App Store plan change the refreshed token kept `chatgpt_plan_type` = free and every paid model failed with "The 'gpt-6-astra' model is not supported when using Codex with a ChatGPT account" until the next refresh — [source: https://github.com/openai/codex/issues/53020 | allowlisted host] (confidence: high)

## Prior Art

- The Codex-native passthrough route already exists and is the closest thing to "pass through ChatGPT Codex models": `litellm/proxy/pass_through_endpoints/codex_passthrough_endpoints.py` serves `GET/POST /backend-api/codex/{models,responses}` by forwarding verbatim to `https://chatgpt.com/backend-api/codex/{endpoint}`, requiring a ChatGPT bearer in `Authorization` plus a separate LiteLLM key in `x-litellm-api-key`, and refusing when the two are the same token. It never consults the router, so an auto-router cannot influence it today — [source: `litellm/proxy/pass_through_endpoints/codex_passthrough_endpoints.py:32-89`] (confidence: high)
- The semantic auto-router already resolves a route to a model name and lets the normal router pick the deployment: `litellm/router_strategy/auto_router/auto_router.py:196-250` returns `PreRoutingHookResponse(model=routed_model, messages=..., routing_decision=...)`, and `litellm/router.py:15374` / `:15539` replace `model` with that value before deployment resolution — [source: `litellm/router_strategy/auto_router/auto_router.py`, `litellm/router.py`] (confidence: high)
- The `/v1/responses` surface already routes through the semantic auto-router: `tests/e2e/router/test_auto_router_regressions_e2e.py:680` pins that `/v1/responses` input is resolved into messages for the pre-routing hook (GitHub PR #37333) and that the routed deployment serves the request — [source: `tests/e2e/router/test_auto_router_regressions_e2e.py`] (confidence: high)
- LiteLLM has no notion of a token plan today. A search for `token_plan|chatgpt_plan|plan_type|subscription_plan` across `litellm/**/*.py` returns zero files, and `litellm/types/utils.py:4358-4364` lists `chatgpt_auth_file` as a server-owned WIF param with no sibling concept of plan or entitlement — [source: `litellm/types/utils.py`, repo-wide grep] (confidence: high)
- The credential precedence a ChatGPT deployment already uses is a three-step fallback, not a plan-aware switch: `litellm/llms/chatgpt/chat/transformation.py:61-69` returns the client credential first, then the configured `api_key`, then the authenticator's stored access token; `litellm/llms/chatgpt/responses/transformation.py:58-91` does the same for the Responses surface and additionally prefers the authenticator over `api_key` when a `chatgpt_auth_file` is set — [source: `litellm/llms/chatgpt/chat/transformation.py`, `litellm/llms/chatgpt/responses/transformation.py`] (confidence: high)
- The internal precedent for attaching target-specific parameters after a routing decision is the complexity router's tier pinning: `litellm/router_strategy/complexity_router/config.py:259-274` carries per-tier `litellm_params`, `litellm/router.py:13697` (`_tier_params_the_target_accepts`) decides which of them the chosen target accepts, and `litellm/router.py` (`_pin_tier_params_onto_request`) applies them on top of the request while dropping client carriers the pin supersedes — [source: `litellm/router_strategy/complexity_router/config.py`, `litellm/router.py`] (confidence: high)
- The alias marker forwarding rules are the hard constraint on any alias-level credential: `litellm/router.py:562-567` puts `api_key`, `api_base`, `api_version`, and `responses_api_version` in `_ALIAS_PARAMS_NEVER_FORWARDED` and keeps `_FORWARDED_CREDENTIAL_ISOLATION_PROVIDERS = {"chatgpt", "anthropic"}`, and `litellm/router.py:16067-16082` forwards only the marker's other params onto the request while dropping any the selected deployment sets itself — [source: `litellm/router.py`] (confidence: high)
- Upstream OpenAI Codex separates plan identity from model visibility rather than encoding entitlement in the model list: `codex-rs/login/src/auth/manager.rs:702` exposes `account_plan_type()` from the id_token's `chatgpt_plan_type` claim, `codex-rs/protocol/src/auth.rs:68-100` maps raw plan strings to a `PlanType`/`KnownPlan` enum (free, go, plus, pro, prolite, promax, team, business, enterprise, edu, sci, and usage-based variants), and `codex-rs/protocol/src/openai_models.rs:1096-1101` (`filter_by_auth`) filters the model catalog only by auth mode (`chatgpt_mode || model.supported_in_api`), not by plan — [source: https://github.com/openai/codex/blob/rust-v0.159.3/codex-rs/protocol/src/openai_models.rs | allowlisted host] (confidence: high)
- Upstream gates a paid-only feature on plan type directly: `codex-rs/core/src/session/token_budget.rs:13-19` (`experimental_context_is_eligible`) requires `AuthMode::Chatgpt` and a plan in `Plus | Pro | ProLite | ProMax` — [source: https://github.com/openai/codex/blob/rust-v0.159.3/codex-rs/core/src/session/token_budget.rs | allowlisted host] (confidence: high)
- Upstream Codex supports a gateway alongside a ChatGPT login with two separate credentials: `codex-rs/core/tests/suite/gateway_auth.rs:33-51` shows an inference request carrying both `authorization: Bearer <chatgpt token>` and `x-gateway-auth: Bearer <gateway token>`, and `codex-rs/model-provider-info/src/lib.rs:468-486` (`to_api_provider`) switches the base URL to the ChatGPT Codex backend for ChatGPT auth modes — [source: https://github.com/openai/codex/blob/rust-v0.159.3/codex-rs/core/tests/suite/gateway_auth.rs | allowlisted host] (confidence: high)
- Other gateways implement the same two-credential shape outside LiteLLM: Zuplo documents "Codex sends your ChatGPT login in the authorization header and authenticates to the gateway separately with the app's API key" with `wire_api = "responses"` and `requires_openai_auth = true` — [source: https://zuplo.com/changelog/2026/10/08/codex-chatgpt-subscriptions | host not on safe list, page not fetched; search-result description only] (confidence: low)

## Market & Context

- OpenAI documents gateway sign-in as a first-class deployment path, and LiteLLM's own cookbook points operators at it: `cookbook/ai_coding_tool_guides/chatgpt_subscription_passthrough.md` links "OpenAI's gateway configuration guide" at `learn.chatgpt.com/docs/enterprise/sign-in-with-chatgpt-through-a-gateway` — [source: `cookbook/ai_coding_tool_guides/chatgpt_subscription_passthrough.md`] (confidence: high)
- LiteLLM's shipped guidance already documents the fallback-vs-subscription tradeoff the idea touches: the same cookbook says "Explicit cross-provider fallbacks can incur separate API charges; do not configure them for subscription-only traffic" and that standard model routes keep the caller's login while "explicitly configured cross-provider fallbacks use their own credentials" — [source: `cookbook/ai_coding_tool_guides/chatgpt_subscription_passthrough.md`] (confidence: high)
- LiteLLM's documented model configuration for a ChatGPT deployment is a plain `chatgpt/` model with `mode: responses` and no saved login, i.e. the caller's credential is the credential — the operator-facing model is one line of YAML — [source: `cookbook/ai_coding_tool_guides/chatgpt_subscription_passthrough.md`] (confidence: high)
- The alternative operators use today is the native Codex route: point Codex at `https://<proxy>/backend-api/codex` and it "does not need a model deployment or resolve model aliases", which means no routing layer, no auto-router, and no chance to swap models — [source: `cookbook/ai_coding_tool_guides/chatgpt_subscription_passthrough.md`] (confidence: high)
- The proxy's own Codex model catalog is built from the proxy's model list, not from the account's entitlements: `litellm/proxy/common_utils/codex_model_catalog.py:391-429` joins `/v1/models` rows with router metadata, and `litellm/proxy/common_utils/codex_bundled_models_0.159.3.json` carries 11 stock models whose `visibility` and `supported_in_api` fields are static catalog metadata — [source: `litellm/proxy/common_utils/codex_model_catalog.py`, `litellm/proxy/common_utils/codex_bundled_models_0.159.3.json`] (confidence: high)
- Community reports show the entitlement error is widely confusing for users: multiple community threads ask why a paid subscriber gets "The 'gpt-5.6-sol' model is not supported when using Codex with a ChatGPT account", including one where the answer was an expired subscription and another where a free plan with Codex credits still could not use the model — [source: https://community.openai.com/t/the-gpt-5-6-sol-model-is-not-supported-when-using-codex-with-a-chatgpt-account-why-pricing-page-says-it-is/1389502 | host not on safe list, page not fetched; search-result description only] (confidence: low)

## Data & Constraints

- The plan type is present in the credential LiteLLM already holds, but LiteLLM does not read it. `litellm/llms/chatgpt/common_utils.py:273-292` decodes JWT claims and reads only `chatgpt_account_id` from the `https://api.openai.com/auth` claim (`OPENAI_AUTH_CLAIM_KEY` at `:41`), while the plan claim lives under that same namespace upstream — [source: `litellm/llms/chatgpt/common_utils.py`] (confidence: high)
- Upstream reads the plan from the id_token, not the access token: `codex-rs/login/src/token_data.rs:44-84` (`IdTokenInfo.chatgpt_plan_type`, `get_chatgpt_plan_type`, `get_chatgpt_plan_type_raw`), and `codex-rs/login/src/auth/manager.rs:702-719` reads `t.id_token.chatgpt_plan_type`. LiteLLM's authenticator persists `id_token` in the auth file (`litellm/llms/chatgpt/authenticator.py:315-325`, `:353-364`, `:373-379`), so the claim is already on disk but unparsed — [source: `litellm/llms/chatgpt/authenticator.py`; https://github.com/openai/codex/blob/rust-v0.159.3/codex-rs/login/src/token_data.rs | allowlisted host] (confidence: high)
- A forwarded client's credential reaches the ChatGPT provider through a scoped header, not a generic parameter: `litellm/proxy/litellm_pre_call_utils.py:4345-4396` (`add_provider_specific_headers_to_request`) puts the caller's ChatGPT bearer into a `ProviderSpecificHeader` scoped to the `chatgpt` provider, and `litellm/llms/chatgpt/common_utils.py:352-363` (`get_chatgpt_request_credential`) reads it back only for that provider — [source: `litellm/proxy/litellm_pre_call_utils.py`, `litellm/llms/chatgpt/common_utils.py`] (confidence: high)
- A forwarded client credential is deliberately isolated to a small provider set, and that isolation is what would keep a plan credential away from a non-ChatGPT fallback: `litellm/router.py:4826-4841` computes `forwarded_authorization` only when `deployment_provider in _FORWARDED_CREDENTIAL_ISOLATION_PROVIDERS` and routes it through `_handle_clientside_credential`, which builds a per-request deployment rather than registering one — [source: `litellm/router.py`] (confidence: high)
- `api_key` is a server-owned parameter, not a client-switchable one: `litellm/types/litellm_params.py:64-99` (`ProviderConnection`) holds `api_key` and `chatgpt_auth_file`, `litellm/types/utils.py:4367-4372` builds `all_litellm_params` from owned wire names, and `litellm/litellm_core_utils/credential_accessor.py` (`reject_api_key_secret_reference`) rejects a client-supplied `api_key` that names a credential holding an `oidc/` secret reference — [source: `litellm/types/litellm_params.py`, `litellm/types/utils.py`, `litellm/litellm_core_utils/credential_accessor.py`] (confidence: high)
- The ChatGPT provider is Responses-only, so a fallback target must be able to serve the Responses contract: `litellm/responses/bridge_check.py:20` lists `chatgpt` in `RESPONSES_ONLY_PROVIDERS`, and `litellm/llms/chatgpt/responses/transformation.py` implements the Responses request path. Chat completions against a `chatgpt/` deployment are not a supported target shape — [source: `litellm/responses/bridge_check.py`] (confidence: high)
- Spend attribution for a plan-covered route is currently unpriced: all 20 `chatgpt/*` rows in `litellm/model_prices_and_context_window_backup.json` have `input_cost_per_token` and `output_cost_per_token` absent, and `litellm/cost_calculator.py:920-931` (`_base_model_pricing_provider`) documents that a `base_model` is what supplies rates for subscription rows — [source: `litellm/model_prices_and_context_window_backup.json`, `litellm/cost_calculator.py`] (confidence: high)
- Plan exhaustion and model ineligibility arrive with different shapes but are not classified separately by the router. `litellm/router_utils/fallback_event_handlers.py:259-266` (`is_bad_request_without_fallback`) treats any 400 from a provider as a bad request that blocks fallback when `fallback_on_unsupported_params` is false, while `litellm/utils.py:7832-7857` (`should_retry`) retries 429. The upstream entitlement failure is a 400 `invalid_request` ("The 'X' model is not supported when using Codex with a ChatGPT account"), and the upstream usage-limit failure surfaces as a 429 with a rate-limit payload — [source: `litellm/router_utils/fallback_event_handlers.py`, `litellm/utils.py`; https://github.com/openai/codex/blob/rust-v0.159.3/codex-rs/core/tests/suite/compact.rs | allowlisted host] (confidence: medium)
- The auto-router's own classification step has a cost and a failure mode: `litellm/router_strategy/auto_router/auto_router.py:249-300` embeds the last user message and bills that embedding to the caller's key, and any classifier failure falls back to the router's default model rather than failing the request — [source: `litellm/router_strategy/auto_router/auto_router.py`; `tests/e2e/router/test_auto_router_regressions_e2e.py:705-714`] (confidence: high)
- The ChatGPT upstream endpoint is fixed to `https://chatgpt.com/backend-api/codex` (`litellm/llms/chatgpt/common_utils.py:38`), and `litellm/llms/chatgpt/common_utils.py:366-379` (`chatgpt_client_api_base`) rejects any client-credential base URL that is not that host over HTTPS — [source: `litellm/llms/chatgpt/common_utils.py`] (confidence: high)
- Upstream does not expose a per-account entitlement list. Codex fetches its catalog from the ChatGPT backend (`https://chatgpt.com/backend-api/codex/models`) and filters it by auth mode only; `codex-rs/model-provider/src/models_endpoint.rs` (`fetch_models`, `resolve_api_provider`) and `codex-rs/model-provider/src/models_identity.rs` (`identity`) key the catalog cache on account id, user id, email, and `account_plan_type`, which means a plan change invalidates the cached catalog rather than filtering it by plan — [source: https://github.com/openai/codex/blob/rust-v0.159.3/codex-rs/model-provider/src/models_identity.rs | allowlisted host] (confidence: medium)

## Evidence Against the Idea

- The core routing-and-credential machinery the idea needs already exists in a narrower form. PR #41522 merged the "client subscription forwarding" path across the router, the proxy pre-call path, and the ChatGPT transformations, so a `chatgpt/` deployment behind an ordinary model group already uses the caller's own ChatGPT OAuth credential, while the alias-level `api_key` stays put and the credential is isolated to `chatgpt` and `anthropic` deployments. Building a new plan-aware credential path may duplicate that machinery rather than extend it — [source: https://github.com/BerriAI/litellm/pull/41522; `litellm/router.py:562-567`, `litellm/router.py:4826-4841`] (confidence: medium)
- "Part of the token plan" is not a property LiteLLM can compute from the model name, and the upstream code says so explicitly. Upstream filters the catalog by auth mode, not plan, and enforces plan entitlement server-side by rejecting the request with a 400. Any LiteLLM-side eligibility rule is therefore a guess about OpenAI's server-side policy, and the public evidence shows that policy changing without notice (a plan tier change, an expired subscription, and a stale `chatgpt_plan_type` claim each produced the same "not supported when using Codex with a ChatGPT account" error) — [source: https://github.com/openai/codex/blob/rust-v0.159.3/codex-rs/protocol/src/openai_models.rs, https://github.com/openai/codex/issues/14190, https://github.com/openai/codex/issues/53020 | allowlisted host] (confidence: high)
- The literal reading of the idea conflicts with how ChatGPT credentials are scoped. "Pass through available ChatGPT Codex models using token plan OAuth" implies the proxy holds the plan credential and picks models from it, but LiteLLM's ChatGPT credential precedence is client-first, and `chatgpt_auth_file` is a per-deployment server-owned parameter that the alias never forwards. A proxy-held plan credential that switches per selected model has no home in the current schema — [source: `litellm/llms/chatgpt/responses/transformation.py:58-91`, `litellm/router.py:562-567`, `litellm/types/utils.py:4358-4364`] (confidence: high)
- The upstream-native surface cannot host the idea at all. `codex_passthrough_route` forwards verbatim to a fixed ChatGPT endpoint and never asks the router, and the alias `/v1/models` catalog is built from the proxy's own model list. Making the Codex-native route consult an auto-router would be a different feature from the one described, with a different request/response contract — [source: `litellm/proxy/pass_through_endpoints/codex_passthrough_endpoints.py`, `litellm/proxy/common_utils/codex_model_catalog.py`] (confidence: high)
- Cost and latency are non-zero and are not in the idea's framing. Every routed request pays for a routing embedding billed to the caller's key, and a plan-covered route currently prices at zero because the `chatgpt/*` rows carry no rates, so a "savings" comparison against an ordinary model has no data behind it — [source: `litellm/router_strategy/auto_router/auto_router.py:249-300`, `litellm/model_prices_and_context_window_backup.json`, `litellm/cost_calculator.py:920-931`] (confidence: high)
- The router's fallback semantics will silently do the wrong thing for a plan-ineligible model. A 400 from ChatGPT is treated as a bad request that blocks fallback when `fallback_on_unsupported_params` is false (`litellm/router_utils/fallback_event_handlers.py:259-266`), so a model outside the plan either fails the request or falls back to whatever the operator configured, neither of which is "use normal proxy auth for the selected model" — [source: `litellm/router_utils/fallback_event_handlers.py`, `litellm/types/router.py:212`] (confidence: medium)
- The existing provider-credential isolation is a good thing that this idea would have to preserve, not extend: LiteLLM deliberately restricts forwarded client credentials to `chatgpt` and `anthropic` and builds a per-request deployment for them, and there is an open bug (#42172) where a third-party `api_base` under `anthropic/` received the client's Claude subscription credential. Adding a proxy-held plan credential that follows a routing decision widens exactly the surface where that class of leak has already appeared — [source: `litellm/router.py:566`, `litellm/router.py:4725-4758`, https://github.com/BerriAI/litellm/issues/42172 | allowlisted host] (confidence: medium)
- There is a cheaper path to the same user-visible outcome that does not require new routing or credential machinery: a plain model group whose deployment is a `chatgpt/` model already inherits the caller's subscription credential, and an operator can put a `chatgpt/` deployment and an ordinary deployment behind two groups with the router's existing fallback configuration. That configuration is limited, but it is configuration rather than code — [source: `cookbook/ai_coding_tool_guides/chatgpt_subscription_passthrough.md`, `litellm/router.py:4826-4841`] (confidence: medium)

## Gaps & Open Questions

- [NEEDS CLARIFICATION: which credential is "the token plan oauth", the proxy's own stored ChatGPT OAuth from a device-code login, or the client's bearer forwarded through the request. The two lead to materially different designs, and LiteLLM's existing precedence is client-first while `chatgpt_auth_file` is per-deployment and server-owned.]
- [NEEDS CLARIFICATION: whether "a different model that isn't a part of the token plan" means a ChatGPT Codex model outside the caller's plan tier, or a non-ChatGPT model entirely, for example a pay-per-token model such as an OpenAI API deployment. The first reading needs entitlement logic; the second needs only credential isolation, which already exists.]
- [NEEDS CLARIFICATION: which surface the feature lives on. The Codex-native passthrough never consults the router, so an auto-router in front of it is a different feature from an auto-router that resolves to a `chatgpt/` deployment through the ordinary `/v1/responses` path.]
- [NEEDS CLARIFICATION: which router is meant. This codebase names both the semantic `auto_router/` deployment and `auto_router/complexity_router` "auto_router", and only the complexity router has per-tier `litellm_params` today.]
- [NEEDS CLARIFICATION: what "normal proxy auth" means concretely on the path in question, the selected deployment's own `api_key`, the inbound virtual key, or the master key, and whether a Responses-shaped request can be served by a non-ChatGPT target at all given `chatgpt` is Responses-only.]
- [NEEDS CLARIFICATION: how a model is judged "part of the token plan". Upstream enforces entitlement server-side and exposes no per-account entitlement list, so the candidates are a static configured list, the plan tier read from the id_token, or an attempt-then-classify-on-error policy. Each has a different failure mode.]
- [NEEDS CLARIFICATION: what happens when the plan's usage allowance is exhausted, retry the same model, fall back to ordinary auth, or fail the request. The upstream shape is a 429 with a rate-limit payload, which the router currently retries and cools down generically.]
- [NEEDS CLARIFICATION: how spend is attributed for a plan-covered route, given the `chatgpt/*` rows carry no rates. Without a pricing rule, plan-covered traffic reads as zero cost in logs and savings.]
- [NEEDS CLARIFICATION: whether the swapped model is reflected in the response envelope and in the Codex streaming shape the client expects, and whether the routing embedding cost is acceptable on every request.]
- [NEEDS CLARIFICATION: whether an operator-configured list of plan-covered models is acceptable given the public evidence that OpenAI's entitlement changes without notice. A stale list silently routes requests the server will reject.]
- [NEEDS CLARIFICATION: what the trigger was. No issue in this repo describes the auto-router-plus-plan combination, so the demand signal for this exact shape is assumed rather than observed.]
