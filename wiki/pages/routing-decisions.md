The router split into `router_strategy/` (pickers) and `router_utils/` (shared helpers) on purpose: strategies are independent `CustomLogger` subclasses that score deployments, while `router_utils/` owns the cross-cutting plumbing; cooldown cache, retry-from-policy, pre-call affinity checks, fallback event handlers, and the auto-router naming contract (S039). New cross-cutting behavior belongs in `router_utils/`; a new picker belongs in `router_strategy/`; mixing them pulls unrelated code into the hot path (S039).

Two TPM/RPM routers coexist intentionally (S030). `lowest_tpm_rpm.py` is the original, in-memory minute-bucket counter. `lowest_tpm_rpm_v2.py` subclasses `BaseRoutingStrategy`, batches Redis writes through a periodic sync task, caches per model rather than per model-group, and uses `redis.mget` plus `redis.incr` so multiple proxy instances converge (S030). The v1 file stays because existing deployments pin it and the v2 surface is not 100% behavior-identical; new deployments should pick v2. Rejected alternative: collapse them; rejected because in-place migration breaks running proxies and the behavior delta (per-model vs per-group keys) is observable to spend logs (S030).

`auto_router.py` exists alongside the manual strategies on purpose (S038). Manual pickers (`simple_shuffle`, `lowest_cost`, `lowest_latency`) optimize one metric the operator names in advance; the LLM-driven routers (`auto_router`, `complexity_router`, `adaptive_router`, `quality_router`) inspect the request and let the model class decide (S038). Manual routers need only the deployment table; LLM routers need at least one extra model in the table to act as classifier, embedder, or evaluator (S038). Rejected alternative: a single router; rejected because the metric-driven and model-driven paths share no scoring code, and forcing one class to import the other drags classifier overhead onto deployments that only want a simple shuffle (S038).

The split between `budget_limiter.py` and `cooldown_cache.py` is responsibility, not overlap (S035, S039). `budget_limiter.py` is a *filter*; it accepts whatever scorer upstream picked and drops deployments that have exceeded their `$ budget_limit` over a `time_period` (S035). `cooldown_cache.py` is a *gate*; it remembers deployments that recently returned an exception or non-2xx and excludes them from the healthy set regardless of which scorer is active (S039). Both compose: a scorer narrows the field, the budget filter enforces spend, the cooldown gate enforces recent health. Rejected alternative: roll spend tracking into the cooldown cache; rejected because the cooldown cache is keyed by deployment id and a short TTL, while budget tracking is keyed by provider + time window and needs a different storage shape (S035, S039).

`tag_based_routing.py` and `budget_limiter.py` are both filters but not the same primitive (S033, S035). Tag routing is structural; it chooses among deployments by intent (team, tier, customer) and runs before scoring. Budget limiting is a financial gate; it runs after scoring and after cooldown, and only subtracts from a deployment that already passed health and intent. Rejected alternative: fold tag filtering into the budget filter; rejected because a deployment can have tags but no budget, and a budget without tags; conflating them forces operators to declare a budget on every tagged deployment (S033, S035).

`savings_baseline.py` is not a strategy; it is the *counterfactual* a complexity router's savings are measured against (S036). The router's own tier ladder names the model traffic would have run without it; the baseline is the priciest model in the hardest configured tier, ranked against a fixed reference request, and always provider-qualified because the spend writer prices the bare string. Rejected alternative: compute savings per request against the picked model; rejected because per-request ranking would force the baseline to know every input shape the deployment can take (S036).
